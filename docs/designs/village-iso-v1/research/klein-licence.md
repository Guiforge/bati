# Licence des sorties FLUX 3 Image Klein (API BFL)

Recherche du 28/10/2026, sur les textes en ligne ce jour-là. Aucun appel payant, aucune clé utilisée.

## Verdict

**Oui sous condition.** Une image Klein obtenue par `api.bfl.ai/v1/flux-3-image-klein` avec notre clé relève des mêmes BFL Developer Terms que FLUX.2 pro (version EU pour nous : propriété au §3.b, pas de revendication au §4.b, usage personnel ou commercial au §4), pas de la FLUX Kommunity License des poids, qui ne vise que qui télécharge ou fait tourner les poids.
Rien ne change par rapport à FLUX.2 pro, et même dans le pire cas (Kommunity applicable), Guillaume est un « Qualifying User » (< 5 M$ de revenu), donc l'usage commercial des sorties resterait permis.
Les conditions, communes aux deux modèles : ne jamais prétendre qu'une image est faite main ni retirer les Content Credentials (§6.i, voir Limites), et ne pas se servir des sorties pour entraîner un autre modèle (§6.c).

## Ce que ça implique pour Bati

- Le champ `licence` de `scripts/provenance.json` reste le même que pour FLUX.2 pro. Seul `model` change. Texte proposé pour un sprite Klein accepté :
  - `"model": "flux-3-image-klein"`
  - `"provider": "Black Forest Labs (direct API)"`
  - `"licence": "BFL Developer Terms §3.b (EU §4.b): the API account holder owns the output, personal or commercial use"` (chaîne identique à l'existant, 393 entrées l'utilisent déjà)
  - garder `prompt`, `seed`, `width`, `height`, `generated` comme aujourd'hui. L-T08 note que le suréchantillonneur de Klein réécrit le prompt côté serveur : la provenance ne rejoue donc pas l'image à l'identique, ce qui est un problème de vérifiabilité, pas de licence.
  - Option, si on veut lever toute ambiguïté pour un relecteur F-Droid : ajouter un champ `"weights_licence_not_applicable": "FLUX Kommunity License v1.0 governs downloaded weights, not API outputs"`. Pas nécessaire.
- `LICENSE` (racine, « NOTE ON THE ARTWORK ») dit « generated with FLUX.2 by Black Forest Labs ». Dès qu'un sprite Klein est accepté, la phrase devient inexacte : écrire « FLUX.2 and FLUX 3 Image Klein ». Même remarque pour `docs/fdroid.md` § *The artwork had no licence we could grant*. La phrase « outputs are not derivatives of the model » de ces deux fichiers vient du vocabulaire des licences de poids (Kommunity §1.a la contient), pas des Developer Terms : elle reste vraie, mais la base juridique de l'API, c'est §3.b/§4.b.
- Code du dépôt : licence MIT (`LICENSE`), assets sous CC BY-SA 4.0. Une sortie Klein possédée par nous (§3.b) peut être placée sous CC BY-SA comme les autres. F-Droid n'exige pour l'art qu'une licence valide permettant la redistribution ; CC BY-SA n'est ni NC ni ND, donc pas d'anti-feature `NonFreeAssets`.

### 2. Propriété, usage commercial, restrictions

Propriété et usage commercial : voir §3.b, §4.b et §4 ci-dessus. Restrictions des EU Developer Terms :
- §6.c : interdit d'utiliser une sortie pour « train, distill or fine tune any other AI models » (et de bâtir un produit concurrent de BFL).
- §6.i : « Remove, disable, alter, obscure, any Content Credentials or represent to End Users or third parties that (i) Outputs are free of content provenance metadata or (ii) any Task or Output was human-generated; »
- §1.c : « "Content Credentials" means machine-readable content provenance metadata or digital watermarks embedded in or attached to Outputs pursuant to the C2PA or similar technical standard(s), recording the AI system that generated the content and its generation history. »
- §3.b(iv) : BFL « may embed Content Credentials or other provenance data in any Output ».
- §3.b : pas de deepfake, pas d'image faisant croire qu'une personne réelle l'a créée ou approuvée.
- Ni mention obligatoire, ni attribution, ni filigrane visible exigés. Aucune interdiction de redistribuer les sorties.

Centre d'aide BFL, « What is C2PA in FLUX-generated images? », https://help.bfl.ai/articles/3705384267-c2pa-in-flux-generated-images
- Les Content Credentials sont attachées à toutes les images de l'API, sur « all FLUX model endpoints that return a final image » (Klein compris).
- Recadrage, compression, ré-encodage cassent la signature ; BFL conseille de garder le fichier original, car « re-encoding or metadata stripping can remove the embedded manifest ».

Pour mémoire, si la Kommunity License s'appliquait (pire cas) :
- §1.a : « For the avoidance of doubt, Outputs are not considered Derivatives under this License. »
- §1.e : Qualifying User = revenu annualisé brut, affiliés compris, sous 5 000 000 US$.
- §2.a : licence accordée pour « solely if you are a Qualifying User, use Outputs, including Outputs from Derivatives, for commercial purposes ».
- §2.d : « We claim no ownership rights in and to the Outputs. »
- §2.e : condition du Qualifying User, filtrer le contenu ou « ensure Output undergoes review for unlawful or infringing content before public or non-public distribution », et « ensure Output includes disclosures (or other indications) that the Output was generated or modified using artificial intelligence technologies to the extent required under applicable law ». Notre revue humaine des sprites (accept) et la mention IA de `LICENSE` couvrent ces deux points.
- §4.b : pas d'usage des sorties pour améliorer un modèle similaire.
- Une offre payante plus tard reste compatible tant que le revenu reste sous 5 M$ ; au-delà, seule la voie API (Developer Terms) tient, ce qui est déjà notre cas.

## Limites et ce qui reste incertain

- **Aucun texte BFL ne dit en toutes lettres « la Kommunity License ne s'applique pas aux sorties de l'API Klein ».** La conclusion repose sur : le §2.b des Developer Terms (l'API relève des FLUX API Terms), le centre d'aide (« All images generated through the BFL API include full commercial usage rights »), le précédent FLUX.2 [klein] 9B (poids non commerciaux, API commerciale), et le billet de lancement qui présente l'API comme voie commerciale séparée. La clause « accessing, using » de la Kommunity License pourrait, lue au pied de la lettre, viser un usage via l'API ; même dans ce cas nous sommes Qualifying User et les sorties commerciales restent permises. Le risque pratique est donc faible, mais pas nul si Bati dépasse un jour 5 M$ de revenu.
- **Content Credentials (§6.i), commun à FLUX.2 pro et Klein, non résolu ici.** Notre chaîne découpe le fond vert et ré-encode (`cwebp`), ce qui retire ou invalide le manifeste C2PA signé par BFL. Lu strictement, §6.i interdit de « remove, disable, alter » les Content Credentials. Le centre d'aide BFL parle de l'édition comme d'un fait normal (ça casse la vérification) sans dire si c'est une violation. Je n'ai pas trouvé de texte BFL qui tranche. Piste à décider par Guillaume : conserver hors APK les originaux bruts de l'API (avec leur manifeste) pour chaque image acceptée, et garder la mention IA de `LICENSE`. Je n'ai pas vérifié si les originaux sont gardés aujourd'hui ailleurs que dans `~/.cache/bati-art-loop/`.
- **CC BY-SA face au §6.c.** CC BY-SA autorise n'importe quel usage, y compris entraîner un modèle, alors que §6.c nous interdit de le faire nous-mêmes. Je comprends que §6.c lie le développeur et pas les tiers licenciés, mais je n'ai pas de source qui le confirme. Même question pour FLUX.2 pro, déjà tranchée de fait par le projet.
- **Google Play** : je n'ai pas lu la politique Play sur les contenus générés par IA. Elle vise surtout les apps qui génèrent du contenu ; des sprites figés ne devraient pas être concernés, non vérifié.
- La date de la Kommunity License v1.0 n'est pas dans le texte (commit Hugging Face « 14 days ago »). Les Developer Terms peuvent changer ; relire leur date de révision avant chaque release qui ajoute des images.
- Je ne suis pas juriste ; cette note lit les textes, elle ne vaut pas avis juridique.
