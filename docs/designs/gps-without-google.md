## Problem Statement

Bati needs outdoor sessions (run, walk, ride) tracked by GPS with the screen off, on phones
without Google Play Services — GrapheneOS, /e/OS, LineageOS — because that is the F-Droid
audience the app already ships to. `expo-location` links `play-services-location` and calls
`getFusedLocationProviderClient()` in `OnCreate`; with a microG substitution it passes the
F-Droid scanner but on a phone without microG it returns nothing, silently, and
`isGooglePlayServicesAvailable()` cannot detect it (GmsCore #2309). Seven open-source Android
sport/tracking apps all use `LocationManager` + `GPS_PROVIDER` directly. So does Bati.

Roadmap 4.19 ranks this P3 Low, "outdoor quests nobody has asked for". The session settled
that the value is the open-source proof (an Expo app with a GMS-free foreground-service GPS
module, built from source by F-Droid) plus a mode that fits the quest loop, not user demand.

## What Makes This Cool

An Expo + React Native app that tracks a 45-minute run with the screen off on GrapheneOS, with
no Google line anywhere in the tree, and F-Droid builds it. Nobody has shown that yet: the
F-Droid React Native doc predates prebuild and Hermes.

## Constraints

- Licence MIT. Apache-2.0 sources (OpenTracks, Traccar Client, Organic Maps) may be copied with
  header + `NOTICE`; GPL sources (GPSLogger, RunnerUp, FitoTrack) are read-only, rewrite.
- APK ratchet 55 MiB (`release.yml`). MapLibre adds ~4 MiB of arm64 `.so`.
- `__tests__/android-permissions.test.ts` fails on any permission without a written
  justification. This feature adds `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`,
  `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`, `WAKE_LOCK`, and removes `INTERNET`
  from `blockedPermissions`. No `ACCESS_BACKGROUND_LOCATION`: the quest starts with the app on
  screen, and a foreground service of type `location` has no duration cap on Android 15.
- Play Data Safety form and privacy policy change: location collected (on device only), one
  network destination (the tile host). This is the app's first network request.
- Dark mode only, Tamagui tokens, no manual memo (React Compiler), one writer per state.
- Time-mode quests (minutes, not reps) are a prerequisite and land first.

## Premises (agreed)

1. Worth doing for the open-source proof, not for demand. (P1)
2. The blocker is runtime, not build: a local Expo module on `LocationManager` is the only path.
   `expo-location` is not in `package.json` today, so there is nothing to remove. (P2)
3. Android is the only shipped platform (no iOS job in CI). (P3)
4. iOS is deferred, not designed: the JS API is platform-neutral, Swift lands when an iOS
   build exists. (P4)
5. **Revised.** The recap shows a real basemap. Tiles come online from one free vector host
   (OpenFreeMap or Versatiles), cached on disk by MapLibre; `INTERNET` leaves
   `blockedPermissions`. Rejected: blank-canvas SVG trace (no basemap), bundled offline packs
   (APK ratchet). (P5)
6. Permission growth and the Data Safety change are accepted cost. (P6)
7. Elevation tier 0 in v1 (distance, duration, pace); tier 1 barometer in v1.1. (P7)

## Approaches Considered

### Approach A: Local Expo module, JS writes points (chosen)
`modules/bati-location`: Kotlin foreground service emits `Location` events to JS; JS filters
and inserts into a `gps_points` table through Drizzle/expo-sqlite like every other write.
Effort M (human ~5 d / CC ~1 d). Risk Med. ~250 lines Kotlin, one migration.
Con: points buffered in the service while Hermes is dead are lost until the restart receiver
relaunches the app; the trace gets a hole.

### Approach B: Local Expo module, Kotlin writes points
Same service, opens the SQLite file natively. Survives JS death. Effort L (human ~8 d / CC ~2 d).
Rejected for v1: two writers to one DB file, migrations mirrored in Kotlin SQL. Upgrade path if
field tests show JS death is common.

### Approach C: `@react-native-community/geolocation` + 60-line Kotlin keep-alive shim
Effort S. Rejected: last release September 2024, new-arch support unverified, and the
permission ratchet would vouch for a dependency Bati does not control.

## Recommended Approach

**A.** Smallest module that owns its whole loop, points stay on the existing write path.

### Native module (`modules/bati-location`, Android only)
- `LocationManager.requestLocationUpdates(GPS_PROVIDER, 1000, 0f, listener)` — the GPSLogger
  call, without its AlarmManager duty cycle.
- Foreground service: `startForeground(id, notification, FOREGROUND_SERVICE_TYPE_LOCATION)`,
  `PARTIAL_WAKE_LOCK`, `START_STICKY`, restart receiver on process death (GPSLogger's
  `RestarterReceiver` pattern, rewritten).
- Events to JS: `{ t, lat, lon, ele, acc, speed, bearing, satellites }` per fix, plus
  `{ providerEnabled }` and a `noFixTimeout` after 30 s without a fix (LineageOS providers that
  declare themselves alive and return nothing).
- JS API: `start(notification: {title, body})`, `stop()`, `addListener()`,
  `requestPermission()` (runtime `ACCESS_FINE_LOCATION`), `getSatelliteCount()`.
  Same signatures on iOS when it comes; today the iOS side is `unavailable` and the quest type
  is hidden.
- Manifest entries via the module's own `AndroidManifest.xml`; each permission justified in
  `__tests__/android-permissions.test.ts` in the same commit.
- Small: for a service restarted by the OS with no JS alive, the service emits nothing and
  waits; JS resumes on next app open via the orphan-session rule below. Native buffering is the
  Approach B upgrade.

### Filtering (JS, at read and at write)
- Start gate: accuracy < 10 m and ≥ 2 satellites for 3 s (RunnerUp mechanism, rewritten).
- Write raw points, reject only accuracy > 50 m and speed > 8 m/s.
- Distance: `Location.distanceTo()` exposed by the module (WGS84, native); JS accumulates
  every 10 m. Segment break on a jump > 200 m. Auto-pause after 10 s without 10 m.
- Elevation: none displayed in v1 (tier 0). Store `ele` anyway so tier 1 has history.

### Storage
- `gps_points` table, `WITHOUT ROWID`, PK `(session_id, t)`, scaled integers
  (`lat_e7`, `lon_e7`, `ele_cm`, `acc_dm`, `speed_cms`). ~180 kB per hour at 1 Hz.
- Written from JS through the existing Drizzle/expo-sqlite connection (WAL is already on),
  one prepared insert per fix inside a batched transaction every 5 s.
- `sessions.gps_ended_at IS NULL` on an existing row = orphan; offer resume on next launch.
- Aggregates (distance, moving time, current pace) live in the session Zustand store,
  banked in memory and committed in `saveSession`, per the "never write game state before it
  is earned" rule.

### Screens
- During the session: numbers only (distance, moving time, pace, GPS status pill). No map.
- Recap and history: MapLibre (`@maplibre/maplibre-react-native`) with one vector style URL,
  trace simplified by Douglas-Peucker at ~5 m. Under the map, one line: "map tiles from
  <host>; your route is never uploaded".
- Battery-killer screen on first GPS quest: explain, deep-link to the OEM battery settings
  (dontkillmyapp list: Xiaomi, Samsung, OnePlus, Huawei).

### Export
- GPX 1.1, pure TypeScript, `time` on every `trkpt`, XSD order `ele`/`time`/`extensions`,
  `gpxtpx` prefix. Shared through the system share sheet. No TCX, no FIT (Garmin SDK licence).

## Open Questions

1. Which tile host: OpenFreeMap (no key, CDN, OSM Liberty style) vs Versatiles (EU-hosted).
   Decide on rate limits and whether the host logs requests; that name goes in the policy.
2. Does F-Droid's builder handle a local Expo module + prebuild? Nothing in the F-Droid docs
   proves an Expo app has been built by their servers. Biggest residual risk of the project,
   larger than the GPS work. Verify on a branch build before writing Kotlin.
3. Field test T5: 45 min, screen off, one loop walked then ridden, on a GrapheneOS or /e/OS
   phone. GPSLogger proves the capture call; nothing yet proves 45 minutes continuous.
4. Battery: 5 to 12 %/h is extrapolated; measure in T5.
5. Does the quest completion (boss damage, resources) key on distance, moving time, or both?
   Product call, needed before the session store changes.

## Success Criteria

- A 45-minute outdoor session on a phone without Google Play Services, screen off, yields a
  trace with no hole longer than 10 s and a distance within 3 % of a known loop.
- `npm test` green including `android-permissions.test.ts` with every new permission justified.
- F-Droid metadata builds the APK with the module, no `scandelete`, no anti-feature.
- APK under 55 MiB.
- The recap map renders from cache with airplane mode on, for a route seen once online.

## Distribution Plan

Existing pipeline: `npm run release` tags, `release.yml` builds the APK and publishes a GitHub
Release; F-Droid picks the tag up via the merged recipe (MR !45076). New: the recipe must be
checked against the local module (open question 2) on a `workflow_dispatch` branch build first.
Play internal track needs the Data Safety form updated before the next upload.
