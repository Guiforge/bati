# Design: Handled errors reach the bug-report mail

Generated by /office-hours on 2026-08-30
Branch: error-breadcrumbs
Repo: Guiforge/bati
Status: APPROVED
Mode: Builder

## Problem Statement

A user reported "backup could not be created" with a screenshot, after granting SAF folder
access. The maintainer cannot act on it. The failure is a *caught* error: `hooks/useBackup.ts:72-75`
calls `reportError("backup.save", error)` then a generic toast; `src/reportError.ts:13-16` is
`if (__DEV__) console.error(...)`, so in release the cause is discarded. 113 call sites in 52 files
share that fate. Crashes, by contrast, already reach the maintainer: `src/crashLog.ts` keeps the last
5 uncaught errors and Settings → Feedback (`app/settings.tsx:578`) opens a pre-filled `mailto:`.

Two things are wrong, in order:

1. **The transport is not reliable.** `android/app/src/main/AndroidManifest.xml:12-18` declares
   `<queries>` for `https` only. On Android 11+ package visibility makes
   `Linking.canOpenURL("mailto:…")` return false on a device with a single mail app, and
   `app/settings.tsx:296-299` then shows "No email app found" with Gmail installed. Reports do
   arrive today, so it works on *some* phones; it fails silently on the ones with one mail app.
2. **Caught errors never enter the log** the mail is built from.

## What Makes This Cool

The Signal move: the moment something fails, the hero sees "Error — [close] [send me the
details]" and one tap opens a mail that already says `[backup.save] Unable to open output stream
for URI: …`. No account, no upload, no SDK. A dead-end toast becomes a conversation.

## Constraints

- No network, no telemetry, no crash SDK — a promise in `docs/legal/privacy.md`, and the reason
  the transport is `mailto:`.
- No new dependency. Everything needed is in the repo.
- Same rules as AGENTS.md: one writer per state, prefer a type over a test, test the path the
  app calls, `ponytail:` on deliberate ceilings.

## Premises (agreed)

1. ~~Crashes already reach the mail~~ → **revised**: the transport must be made reliable first
   (`<queries>` for `mailto`). Everything else lands in an inbox some users cannot open.
2. Doing nothing means every non-crash report stays unactionable. It already happened once.
3. Transport stays `mailto:` — Signal / F-Droid pattern, and the privacy promise.
4. Breadcrumbs may contain a chosen folder URI or filename. Acceptable because the mail is
   readable before sending; must be named in the privacy text.
5. The right moment to offer sending is the failure itself, not only the Settings row.

## Cross-Model Perspective

Codex was unavailable (401, `codex login`); a fresh-context Claude subagent read the code.

- **Challenged premise 1** — verified in the manifest, adopted (see above). Proof on a device:
  `adb shell pm query-activities -a android.intent.action.VIEW -d "mailto:x@y"` resolves from the
  shell while the app's `canOpenURL` returns false.
- **Real gap named**: the unattended launch path `src/autoBackup.ts:121-129` has no UI surface;
  a failure there silently turns auto-backup off. The error log row is the *only* thing that
  will ever explain a folder that "forgot itself". Its own `ponytail:` comment says
  "`reportError` writes to a dev console nobody ships" — to be updated.
- **No real import cycle today** (`crashLog → db/preferences → db/client` never reaches
  `db/migrate.ts`); the sink is still right because `src/widget.tsx` (headless task) imports
  `reportError` and must not pull `Platform` + DB at module scope.
- **Intent size is fine**: ≈ 80 KB URL-encoded, far under the Binder limit.
- **SAF messages carry the cause only partly**: `expo-file-system` throws "Missing 'WRITE'
  permission" / "Unable to copy file or directory: …" with no URI; only
  `SAFDocumentFile.kt` "Unable to open output stream for URI: content://…" embeds one.
- Proposed a share-sheet `.txt` fallback and a "folder exists / label" probe line in the
  `backup.save` catch. Both deferred (Approach C).

## Approaches Considered

- **A — Minimal, plumbing only**: manifest query, sink, error log, second mail section. No
  alert, no hook. Rejected: the blocked hero still sees a 3-second toast and has to guess that
  Settings › Feedback exists.
- **B — Audited plan + step 0** (chosen).
- **C — B + share-sheet fallback + SAF probe line**: deferred. Two transports for one content is
  two paths to test and document before a single report has proven the fixed `mailto:` is not
  enough. Reopen when a report arrives that says "no email app" with the query in place, or one
  that cannot tell which folder failed.

## Recommended Approach — B

Step 0 first, the rest is the audited plan in `~/.claude/plans/les-feedback-fonctionne-bien-indexed-flask.md`.

0. **Transport.** `plugins/withAndroidMailtoQuery.js`, same shape as
   `plugins/withAndroidTrimPermissions.js`: add
   `<intent><action android:name="android.intent.action.VIEW"/><data android:scheme="mailto"/></intent>`
   to `<queries>` via `withAndroidManifest` (`manifest.queries[].intent[]` is typed; the
   existing `https` query comes from expo's `Scheme` mod — append to `queries[0].intent`).
   A new test reads the **committed** `android/app/src/main/AndroidManifest.xml` and regexes
   `android:scheme="mailto"` inside `<queries>` — proving the prebuild output, not the plugin
   source (`require`ing the plugin pulls ESM jest cannot parse; `android-permissions.test.ts`
   scans node_modules manifests, a different job).
1. **`src/reportError.ts`** — `setErrorSink(fn)`, 3 lines, no imports; `sink?.(context, error)`
   after the dev `console.error`.
2. **`src/crashLog.ts`** — `append(key, cap, report)` shared by `recordCrash` and a new
   `recordHandledError`; row `errorLog`, cap 20, consecutive identical `context+message`
   collapse into `count`, message truncated to ~300 chars, writes serialised by a promise chain
   (no re-entrancy flag: `recordHandledError` cannot loop — verified `db/preferences.ts` and
   `db/client.ts` never call `reportError`). `installCrashHandler()` installs the sink.
   A collapsed entry updates `at` to the latest occurrence. `readErrorLog()` mirrors
   `readCrashLog()`. `buildBugReportMailto(crashes, handled, version, strings)` renders a second
   section; `BugReportStrings` gains `errorsHeader` / `noErrors` so both callers must supply them.
   `clearCrashLog` is left alone (no app caller today; not extended).
   Timing: `db/migrate.ts:258` and `backupBeforeMigrations` call `reportError` *before* migrations
   run; the sink write is swallowed on failure like `recordCrash`, and on a first launch the
   `user_preferences` table may not exist yet — that entry is lost by design, not retried.
   Known gap: `src/widget.tsx` (headless task) imports `reportError` but the sink is installed in
   `app/_layout.tsx`, so widget-task failures never reach the log. Name it in the sink's comment.
   The Settings row keeps showing the **crash** count only; handled errors do not count toward
   it, so "3 reports" stays honest on a healthy app.
3. **`hooks/useBugReport.ts`** (new) — `openBugReport` + crash count lifted from
   `app/settings.tsx:276-307`, plus `alertWithReport(message)` =
   `Alert.alert(t("common.error"), message, [close, feedback.report_cta → openBugReport])`.
   Lives here, not in `useBackup`, so the next failing screen calls it instead of copying it.
4. **`hooks/useBackup.ts`** — the five catch-block `showError` calls become `alertWithReport`:
   four `backup.exportFailed` (`:57,74,96,113`) and `backup.importFailed` (`:139`), same class of
   caught error. Validation rejections (`backup.rejected.*`, `:129-133`) stay toasts: a verdict
   on the chosen file, not a failure.
5. **i18n** — three keys in `feedback`: `report_cta`, `errors_header`, `no_errors`. Title and
   close button reuse `common.error` / `common.close` (`common.ok` does not exist).
6. **Privacy text** — `docs/legal/privacy.md` § Crash reports (en + fr) and
   `privacy.crashes_body` in `locales/*.json`: "crashes and recent error messages, which may
   include the name of a folder you chose". Update the `ponytail:` notes in `src/crashLog.ts:20-22`
   and `src/autoBackup.ts:123-128` that describe this work as not done.

## Open Questions

None. (Resolved during review: RN's `IntentModule.canOpenURL` uses `resolveActivity`, which is
visibility-gated; `openURL` does not check, so it works without the query. The query is still
added: it is the documented fix, keeps the honest "no mail app" toast, and the test makes it
permanent.)

## Hardware verification (2026-08-31, Fairphone 6, /e/OS, Android 16)

- The whole pipeline proved itself unprompted: the device's remembered backup folder was renamed
  before first launch of the new build, the daily auto-backup failed, and Settings → Feedback
  produced a mail carrying `--- Erreurs récentes --- [1] … (backup.auto.daily) — Call to function
  'FileSystemFile.copy' has been rejected. → Caused by: The destination path does not exist` —
  exactly the line the original user report lacked.
- The single-mail-app `canOpenURL` failure did NOT reproduce on this device: /e/OS's bundled mail
  app is a system app, visible without `<queries>`. The declaration ships preventively for stock
  devices whose only mail app is a user app; the manifest test keeps it.

## Success Criteria

- On a dev build with exactly one mail app, Settings › Feedback opens the mail client.
- Save-to-folder into a Google Drive folder fails → Alert with "send me the details" → mail body
  contains `[backup.save]` and the native message.
- Reopen the app, Settings › Feedback: same entries (persisted, not in-memory).
- `__tests__/crashLog.test.ts`: `installCrashHandler()` + `reportError()` → `readErrorLog()` has
  the entry; two calls in one tick → two entries; 25 identical → 1 entry `count: 25`;
  25 distinct → 20; a breadcrumb never evicts a crash; both mail sections render.
- `__tests__/useBackup.test.ts` mocks `@/hooks/useBugReport` (as it already mocks Toast and
  reportError) and asserts `alertWithReport` was called with `backup.exportFailed` /
  `backup.importFailed` (`:222` and `:183` rewritten). A small `__tests__/useBugReport.test.ts`
  spies `Alert.alert` (the `paused-overlay.test.tsx:191` pattern) and asserts the second button's
  `onPress` opens the mailto — state, not navigation.
- `npm run check`, `npm test`, `npm run deadcode`, `nvm exec 24 npm test` green.
